WeHelp 記帳專案 · 本週筆記

登入只是門牌，
真正的鎖在資料庫規則

這週把純前端的記帳頁，升級成有會員的版本：用 Firebase Authentication 註冊與登入，紀錄存進 Firestore，而且每個人只能讀寫自己的資料。重點不是「接上 Firebase」，而是搞懂前端的登入判斷防不了誰，真正的權限要寫在 Firestore Security Rules。

01 — 總覽

本週做了什麼

幾件事串成一條線：使用者在首頁註冊或登入 → 取得 uid → 進入記帳頁 → 紀錄寫進以 uid 命名的路徑 → 規則確認「這個 uid 只能碰自己的路徑」。

01 安裝 firebase 與環境變數範例.env.example 列出六個 NEXT_PUBLIC_FIREBASE_* 欄位 設定
02 Firebase 初始化src/lib/firebase.ts:檢查設定、避免重複初始化、統一錯誤訊息 lib
03 useAuth 與 AuthProvider提供 signUp / signIn / logOut,並在根 layout 包住整個 app hook
04 首頁登入與註冊區塊同一頁並排兩個表單;已登入顯示「立刻開始」與「登出」 UI
05 記帳頁需登入,資料庫成功後才更新列表useRecords(uid) 讀、新增、刪除都走 Firestore hook + UI
06 Firestore 規則firestore.wehelp.rules:只允許會員讀寫自己的紀錄,並檢查欄位格式 規則

02 — 設定

Firebase 的設定可以公開嗎

.env.example 裡六個欄位全部以 NEXT_PUBLIC_ 開頭。這個前綴的意思是：Next.js 會在建置時把值直接塞進送給瀏覽器的 JavaScript，所以誰都看得到。

對 Firebase 來說這是正常的。apiKey 只是用來辨識是哪個專案,不是密碼,拿到它並不能讀取你的資料。能不能讀寫,取決於 Auth 與 Security Rules。反過來說,如果你把規則開成 allow read, write: if true,不管 key 藏得多好,資料庫都是對全世界敞開的。

東西能不能公開為什麼
NEXT_PUBLIC_FIREBASE_*可以只是專案識別,不能單獨用來存取資料
Security Rules可以公開規則本身不是祕密,重點是寫對
Admin SDK 的服務帳戶金鑰絕對不行可以繞過所有規則;這個專案沒有用到,也不該放進前端

初始化時的兩個小設計

// 已經初始化過就重用,避免 Next.js 熱重載時重複初始化而報錯
return getApps()[0] ?? initializeApp(firebaseConfig);

// 缺少任何一個環境變數,直接丟出看得懂的錯誤
throw new Error(`缺少 Firebase 環境變數:${missing.join(", ")}`);

缺設定時如果不檢查,Firebase 會丟出難懂的內部錯誤。先檢查、再明講缺哪幾個,除錯快很多。missingFirebaseConfig() 另外給 UI 判斷,讓頁面顯示「缺少 Firebase 環境變數」而不是整頁壞掉。

03 — 登入

登入狀態:useAuth 與 Context

登入狀態是整個 app 都要用的資料(首頁、記帳頁都要知道是誰),所以用 React Context 放在根 layout 的 AuthProvider,任何元件呼叫 useAuth() 就拿得到,不必一層一層傳 props。 

// 不是「登入完成後去讀 user」,而是訂閱狀態變化
useEffect(() => {
  if (missingFirebaseConfig()) return;
  return onAuthStateChanged(getFirebaseAuth(), (next) => {
    setUser(next);
    setLoading(false);
  });
}, []);

onAuthStateChanged 會在頁面載入時先檢查「之前登入過沒有」(Firebase 預設把登入狀態存在瀏覽器),所以重新整理後仍保持登入。回傳值是取消訂閱的函式,直接當 useEffect 的清理函式回傳,元件卸載時就會自動取消。

為什麼要有 loading 狀態

重新整理的瞬間,Firebase 還在確認登入狀態,此時 user 是 null,但不代表「沒登入」。如果沒有 loading,畫面會先閃一下登入表單,記帳頁甚至會誤判成未登入而把人踢走。所以 loading 為 true 時一律顯示「載入中…」。

signUp / signIn 回傳布林值

兩個函式成功回傳 true、失敗回傳 false,錯誤訊息存在 error 狀態。呼叫端(表單)只需要知道成不成功:成功就清空輸入框,失敗就顯示訊息。不必自己寫 try/catch,也不必認識 Firebase 的錯誤格式。

錯誤訊息統一

"auth/invalid-credential": "email 或密碼錯誤。",
"auth/wrong-password":     "email 或密碼錯誤。",
"auth/user-not-found":     "email 或密碼錯誤。",

帳號不存在與密碼錯誤給同一句話。如果分開說「查無此帳號」,攻擊者就能用登入頁一個一個試出哪些 email 有註冊。這叫避免帳號列舉(account enumeration)。

04 — 觀念

頁面守門不等於安全

記帳頁用 useEffect 判斷:載入完成而且沒有 user,就 router.replace("/") 導回首頁。這是好的使用者體驗,但不是安全機制。 

useEffect(() => {
  if (!authLoading && !user) router.replace("/");
}, [authLoading, user, router]);

原因很單純:這段程式碼跑在使用者的瀏覽器裡。使用者可以停用 JavaScript、改程式碼、或根本不開網頁,直接拿你公開的 Firebase 設定去呼叫 Firestore。前端的判斷全部可以被繞過。

原則

前端判斷負責體驗(別讓沒登入的人看到空白頁);權限判斷負責安全,必須放在使用者碰不到的地方,也就是 Firestore Security Rules。

用 router.replace 而不是 push,是因為 replace 不會在瀏覽紀錄留下記帳頁,使用者按「上一頁」不會又被彈回來、再被導走,陷入來回跳。

05 — 規則

Firestore 規則:真正的鎖

資料放在 wehelpAccounting/{uid}/records/{recordId}。路徑裡的 {uid} 是萬用字元,規則拿它跟登入者的 request.auth.uid 比對: 

match /wehelpAccounting/{uid}/records/{recordId} {
  // 讀取、刪除:登入,而且路徑裡的 uid 就是自己
  allow read, delete: if request.auth != null && request.auth.uid == uid;

  // 新增:除了身分,還要檢查資料長相
  allow create: if request.auth != null
    && request.auth.uid == uid
    && request.resource.data.keys().hasOnly(["type", "amount", "description", "createdAt"])
    && request.resource.data.type in ["income", "expense"]
    && request.resource.data.amount is number
    && request.resource.data.amount > 0
    && request.resource.data.description is string
    && request.resource.data.description.size() > 0
    && request.resource.data.description.size() <= 200
    && request.resource.data.createdAt == request.time;
}
條件在擋什麼
request.auth != null沒登入的人
request.auth.uid == uid已登入,但想讀寫別人路徑的人
keys().hasOnly([...])夾帶多餘欄位(例如偷塞 isAdmin)
type in [...]亂填收支類型
amount is number 且 > 0金額寫成字串、負數、零
description 長度 1 到 200空說明、塞超大字串
createdAt == request.time偽造時間;要求用伺服器時間

三個值得記的地方

沒有 update 規則 = 不能修改。 規則是「預設拒絕」,沒有明確允許的操作一律被擋。目前介面只有新增與刪除,所以只開這兩個(加上讀取),不多給權限。這叫最小權限原則。

規則會再驗證一次前端已經驗過的東西。 Form.tsx 已經擋了空說明、金額小於等於 0,但前端驗證只是方便使用者;規則裡再驗一次,才是真的擋得住繞過前端的請求。

createdAt == request.time 搭配 serverTimestamp()。 前端寫入時送的是佔位符 serverTimestamp(),Firestore 在伺服器端換成當下時間,同時規則裡的 request.time 也是同一個值,兩者相等才放行。這樣使用者就沒辦法自己填一個假的日期。

部署注意

repo 裡的 firestore.wehelp.rules 只是規則片段,寫了不會自動生效。要貼到 Firebase 主控台的 Firestore 規則頁(或合併進專案原本的規則檔再部署)。沒貼的話,程式會因為預設拒絕而收到 permission-denied。

06 — 資料

紀錄:先寫入成功,再更新畫面

這週有一個提交的標題是「資料庫成功後才更新列表」。對照兩種寫法: 

// 做法 A:先改畫面,背景再寫資料庫(樂觀更新)
setRecords((prev) => [record, ...prev]);
addDoc(...);          // 失敗了?畫面上卻已經有這筆

// 做法 B(本專案):等資料庫回應成功,才改畫面
const ref = await addDoc(recordsCollection(uid), { ... });
setRecords((prev) => [{ ...record, id: ref.id }, ...prev]);

做法 B 會慢一點點,但畫面永遠跟資料庫一致:被規則擋下、網路斷線時,不會出現「看起來新增了、重新整理就消失」的假象。記帳的資料不能騙使用者,所以選保守的做法。同時 ref.id 是 Firestore 產生的文件 id,先等到才有,畫面上的新紀錄才能立刻被刪除。

Form 的 onAdd 回傳 Promise<boolean>,成功才清空輸入框;失敗時保留使用者已輸入的內容,不用重打。送出期間 submitting 為 true,按鈕停用並顯示「新增中…」,避免連按重複新增。

切換使用者時重設狀態

if (uid !== loadedUid) {
  setLoadedUid(uid);
  setRecords([]);
  setLoading(Boolean(uid));
  setError(null);
}

登出再用另一個帳號登入時,uid 變了,上一個人的紀錄必須立刻清掉,否則在新資料載入前畫面會短暫顯示前一個人的帳。這是 React 官方認可的「在 render 中依 props 調整 state」寫法,比在 useEffect 裡重設更不容易閃一下舊畫面。

避免過期的回應覆蓋新狀態

useEffect(() => {
  let cancelled = false;
  getDocs(...).then((snapshot) => {
    if (cancelled) return;   // 已經換人或離開頁面,丟掉這份結果
    setRecords(...);
  });
  return () => { cancelled = true; };
}, [uid]);

請求是非同步的:如果請求還沒回來使用者就登出,晚到的結果不該被寫進畫面。清理函式把旗標設成 true,回來時直接忽略。這是處理 race condition 的基本手法。

小計怎麼算

total 是用 reduce 累加:收入加、支出減。它是由 records 即時算出來的衍生資料,不另外存成一個 state,這樣不會有「紀錄變了、小計忘了更新」的不一致。

07 — 除錯

容易踩的坑

下面是讀這週程式碼時整理出來、最容易出狀況的地方。

寫入被拒絕:permission-denied

最常見的原因是規則沒有貼到 Firebase 主控台,或欄位與規則不符(多一個欄位、amount 傳成字串)。專案在 errorMessages 裡把這個錯誤翻成「沒有權限寫入資料庫。請確認 Firestore 規則…」,直接把線索告訴使用者。

讀取失敗:要建索引嗎

查詢用了 orderBy("createdAt", "desc")。單一欄位排序 Firestore 會自動建索引,所以不用手動處理;但之後如果加上 where 搭配 orderBy,就可能被要求建立複合索引,錯誤訊息裡會附建立連結。

目前只讀一次,不會即時同步

useRecords 用的是 getDocs(讀一次),不是 onSnapshot(即時訂閱)。所以同一個帳號在兩個分頁操作,另一邊要重新整理才看得到。這是刻意的簡化:新增與刪除時本機自己更新畫面就夠用。需要多裝置同步時再換成 onSnapshot。

金額是數字,不是字串

<input type="number"> 的 value 一律是字串,必須 Number(amount) 轉換後再寫入;否則規則的 amount is number 會擋下來。讀取時也用 Number(data.amount) 保底。

環境變數改了要重啟

NEXT_PUBLIC_* 是建置時寫進程式碼的,改 .env.local 後必須重啟 npm run dev(部署則要重新 build)才會生效。並且 .env.local 不能進版控,repo 只放 .env.example。

最大的陷阱

測試階段為了方便把規則改成 allow read, write: if true,然後忘了改回來。這等於任何人都能讀寫、刪光整個資料庫。上線前務必確認規則已經收緊。

08 — 驗收

怎麼驗收

規則正確與否,光看畫面看不出來。除了正常流程,更要測「不該成功的事」真的失敗。下面是我打算逐項確認的清單(勾選留給實際測過之後填):

正常流程

  • 首頁註冊新帳號,成功後自動呈現已登入狀態
  • 登出後用同一組帳密登入
  • 點「立刻開始」進入記帳頁,新增收入與支出各一筆,小計正確
  • 重新整理頁面,仍保持登入且紀錄還在
  • 刪除一筆,重新整理後不會再出現

應該要失敗的情況

  • 密碼少於 6 字元註冊 → 顯示「密碼至少要 6 個字元」
  • 重複註冊同一個 email → 顯示「這個 email 已經註冊過了」
  • 密碼錯誤與帳號不存在 → 訊息相同
  • 未登入直接開 /accounting → 被導回首頁
  • 用帳號 A 登入後,在 Firebase 規則模擬器以 A 的身分讀 B 的路徑 → 被拒絕
  • 模擬器測試新增時多帶一個欄位,或 amount 為字串 → 被拒絕
  • 模擬器測試 update → 被拒絕
工具

Firebase 主控台的 Firestore 規則頁有「規則遊樂場」,可以指定「已驗證 / 未驗證」、填入 uid 與路徑,直接模擬讀寫是否被放行,不需要真的寫程式去試。

另外跑一次 npm run lint 與 npm run build,確認沒有型別或 lint 錯誤。

09 — 附錄

名詞速查

uid
Firebase Auth 替每位使用者產生的唯一識別碼。這個專案用它當資料路徑,規則也靠它判斷是不是本人。
Security Rules
Firestore 的伺服器端權限規則,預設拒絕,有明確允許才放行。真正的存取控制在這裡。
request.auth
規則中代表「發出請求的登入者」,未登入時為 null。
serverTimestamp()
寫入時由伺服器填入當下時間的佔位符,避免使用者電腦時間不準或被竄改。
onAuthStateChanged
訂閱登入狀態變化的函式,頁面重新整理後也會觸發,回傳取消訂閱的函式。
React Context
讓深層元件不必逐層傳 props 就能取得共用資料。AuthProvider 用它提供登入狀態。
NEXT_PUBLIC_
Next.js 的環境變數前綴,代表會被打包進前端程式碼,所以只能放可公開的值。
最小權限
只開放必要的操作。沒有 update 的介面,規則就不給 update。
帳號列舉
藉由不同的錯誤訊息推測哪些帳號存在的攻擊手法,統一錯誤訊息即可避免。
permission-denied
Firestore 因規則不允許而拒絕請求時的錯誤代碼。
